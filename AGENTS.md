# Repository instructions

- Keep the upstream workload: YOCO-3B (`--arch yoco_3b`) with the upstream `scripts/train.sh` arguments and the deviations in `docs/training.md` (8 data-parallel ranks, `--zero-sharding os`, `--seed 1`, `--save-dir`): one 2,048-token sequence per GPU, `--update-freq 1`, BF16 with FP32 master weights and FP32 Adam state, Adam (0.9, 0.95) with eps 1e-6 and weight decay 0.05, clip norm 2.0, learning rate 1.5e-4 with 50 warm-up updates and polynomial decay over 300,000. Do not change the model, the data or its order, the loss, the optimizer or learning-rate semantics, or the random-number consumption to gain speed. No FP8, INT8 or FP16.
- The 2.12× (2.1247×) headline is a per-update benchmark from a full check (reference → candidate → reference on one host in one session, then numerical gates) on 8 NVIDIA L20Z GPUs. A 20,000-update run was 1.91× faster end to end. Do not present the headline as a time-to-quality or end-to-end speedup, and do not imply that the 3× goal was reached.
- Switches are off by default; the measured configuration is `scripts/configs/faster.env` (identical values in `.harness/config.json` and `optimizations/fused_adam_qkvg.json`). `YOCO_COMPILE_NORM` is set but superseded by `YOCO_TRITON_NORM`. `YOCO_ZERO1_PARAM_VIEWS` needs `YOCO_ZERO1_ALLGATHER`; `YOCO_GRAD_REDUCE_OWNER` needs `YOCO_ZERO1_PARAM_VIEWS` and `YOCO_PARAM_ALLREDUCE`; `YOCO_OWNER_EMBED_GRAD` and `YOCO_CE_REDUCE` need `YOCO_GRAD_REDUCE_OWNER`; `YOCO_Z1_SCALE_KERNEL` needs `YOCO_Z1_ONE_PASS`. The switches were only run with 8 ranks, `--zero-sharding os`, `--bf16` and one 2,048-token sequence per GPU.
- Numerical status: not bitwise identical to the reference (5,123 of 38,464 recorded tensors). It passed every exact item and the 3-seed, 200-update statistical gate. In a paired 2-seed, 20,000-update comparison it stayed within the reference's seed-to-seed difference on the held-out mix and fineweb-edu at 10/10 checkpoints, code at 5/10 and training loss at 7/10, with all four at the final checkpoint; its held-out loss is consistently slightly higher (+0.0024 and +0.0082 bits on average for the two seeds), which two seeds cannot resolve. No downstream evaluation was run. Do not claim lossless acceleration or fill in quality numbers from the paper.
- Memory: peak allocated per GPU is 56.4 GiB vs 52.1 GiB in the check and 55.4 vs 48.3 GiB in the 20,000-update run (copy-engine staging buffers). Full fairseq checkpoints (consolidated optimizer state) and resuming with the switches on have not been tested; the validation saved model weights only.
- Before trusting a timing, check the log for `skipping cudagraphs due to`, recompile-limit messages and `gradient overflow`, time only steady-state updates after compilation, and alternate reference and candidate in independent processes on the same host. Bitwise records do not carry over between hosts, even of the same model: re-verify the unmodified reference on a new host before comparing records.
- The research harness (judge, numerical adapter, reference records and trajectories) is a separate artifact and is not included; `docs/judge.md` describes it. Work after the final configuration (rounds 26–28) is not included. Put new experiments in a new dated directory with source commit, dependency versions and hardware.
- Respect shared-host GPU locks and never stop another user's job. Use public datasets only. Never commit datasets, checkpoints, profiler traces, credentials, private paths, host names or per-file data listings.
